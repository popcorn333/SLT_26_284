TAN-6 Symphony token-consumption observations and assumptions
Updated: 2026-07-14 Europe/London

Scope
-----
This file records measurements from the Codex session used by Slurm job 10800101
(symphony-dtdm-unet) and the current Linear workpad for TAN-6. Values are gross
model token counters, not a statement of billable usage. Cached input may be
weighted differently by the Codex usage limit.

Measured high-consumption interval
----------------------------------

Composition and cause
---------------------
Approximately 99.5% of the increase was cached input. Each small scheduler poll
was processed with about 188000 input-context tokens. Model/tool cycles occurred
roughly every 15--40 seconds because the active Codex turn issued scheduler
checks with short waits (commonly 30 seconds), plus model and tool latency.

The previous Symphony configuration also used polling.interval_ms=15000 for
Linear tracker refreshes and agent.max_turns=100. The 15-second tracker interval
was distinct from the within-turn scheduler polling, but frequent refreshes and
immediate continuation made repeated agent activity easier.

Mitigation now configured
-------------------------
Symphony's Linear tracker interval is 900000 ms (15 minutes). Workflow guidance
requires dependency-aware Slurm jobs, ending the Codex turn after job submission,
no Codex polling of running jobs, and resumption only on an external state change
or after at least 15 minutes.

Linear workpad size assumption
------------------------------
At measurement time, visible TAN-6 issue text was 9906 characters and 1311
whitespace-separated words. The maintained workpad was 5987 characters. Its
standalone size was estimated at roughly 1600--2000 tokens, but the approximately
188000-token active session context was overwhelmingly accumulated Codex history,
tool calls, and tool results rather than the Linear workpad alone.
